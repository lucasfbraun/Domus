# Backup schedule is an hourly due-check against a DB setting, not a dynamic cron expression

**Status**: accepted

The admin needed to configure, from the UI, how often database backups run automatically (daily/weekly/monthly, or off) and how many to retain. Laravel's scheduler (`routes/console.php`) is evaluated once when the scheduler process boots each tick — there's no built-in way to say "run on whatever interval is currently in the `backup_settings` row," because a `Schedule::job(...)->daily()`-style definition is a static cron expression baked into that file, not something the framework re-reads per-request from the database.

Two shapes were considered: generate/rewrite a real cron expression (or a separate system cron entry) whenever the admin saves the setting, or register one fixed, frequent schedule entry that always runs and — in code, on every tick — decides whether a backup is actually due right now. We chose the latter (`Schedule::job(new RunScheduledBackupJob)->hourly()`, delegating the decision to `BackupScheduleService::runIfDue()`), because:

- It needs no process to regenerate/reload cron config on save — changing the setting from Admin → Configurações takes effect on the very next hourly tick, nothing to restart or re-provision.
- It works identically in every environment this app runs in (Sail, plain `php artisan schedule:run` via system cron) without shelling out to rewrite crontab entries, which `DatabaseBackupService`'s sqlite-only, no-external-dependencies philosophy (ADR 0005) already leans away from.
- "Due" only needs hour-level precision for daily/weekly/monthly options — nobody is asking for a specific minute — so polling hourly and comparing against `BackupSetting::last_run_at` is exact enough while staying a single, simple, always-safe-to-re-run check.

`BackupSetting::run_at_hour` (0–23, default 3am) is checked first in `BackupScheduleService::isDue()`, before the interval math: without it, a Daily schedule would fire at whatever hour happens to be current the moment 24h have elapsed since the last run, drifting away from whatever time the admin actually wants backups to run (typically off-peak, and clear of the 09:00/10:00 billing and reminder jobs already in `routes/console.php`). Because of this, `BackupFrequency::nextDueAt()` only has to reason about whole *days* — it anchors on `last_run_at->startOfDay()` before adding the interval, deliberately dropping the time-of-day component, since `isDue()` already handles that separately. A first-ever run (`last_run_at` is null) is "due" the first time the clock hits the configured hour, not immediately on save — enabling the schedule at 2pm doesn't fire a backup at 2pm if the configured hour is 3am, it waits for the next 3am.

`addDay()`/`addWeek()`/`addMonthNoOverflow()` build that day-level offset — the `NoOverflow` variant matters: a plain `addMonth()` from the 31st of a 31-day month rolls into the *next* month rather than clamping to the last day of the shorter one (the exact bug already found and fixed once this session in `DemoSeeder`, see the "fotos de vistoria" work — same footgun, avoided here from the start).

`last_run_at` lives on `BackupSetting`, not derived from the newest file in `DatabaseBackupService::list()` — a manually-triggered backup (Admin → Backups → "Gerar backup") must not reset the automatic schedule's clock, and a pruned/deleted automatic backup must not make the scheduler think none has ever run. Retention (`BackupSetting::retention_count`) is enforced by `DatabaseBackupService::prune()`, called after every backup-creating action (`store()`, `import()`, and `BackupScheduleService::runIfDue()` alike) — the cap is on the whole pool of stored backups, not just ones the automatic schedule made, so a run of manual backups can't quietly bypass it.

**Addendum**: the hour-gate described above (a first-ever run waits for the configured hour, never fires immediately on save) was reported as "I set it to 16:00 and no backup was generated" — the admin had saved the setting *after* 16:00 had already passed that day, so per the design, it correctly waits until 16:00 the *next* day, but nothing on screen said so. `BackupScheduleService::nextRunAt()` now computes that next actual run moment (clamping an overdue due-date to today, then rolling to tomorrow if today's hour has already passed) and `BillingSettingController::edit()` exposes it as `backup_next_run_at`, shown on the Configurações page next to "Último backup automático." This doesn't change `isDue()`'s firing behavior at all — it's purely a "here's what to expect and when" readout, so a correctly-waiting schedule doesn't read as a broken one.
